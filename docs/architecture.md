# Architecture

Each rule in Wishbone lives in one function, and nothing else repeats it. This page says where each rule lives, and what a change to it must touch. It is for a person or an agent who changes the server. To build and run the project, see [`development.md`](development.md). For what Wishbone does, see [`spec.md`](spec.md).

A change that touches one of these rules changes its function and the tests for it. If it adds a copy of the rule, a client can see two answers to the same question.

## Collections, edits, and versions

Every collection and every `PATCH` is built from the same pieces. Copy `GET /users` and `PATCH /users/{id}` (`internal/server/users.go`). The rules are in [API principles](spec.md#api-principles).

- **A collection.** List the sort keys in a `[]page.Key`, the default first (`internal/page`). Put a `collectionRules` on the operation: it makes an unknown filter a 422 `unknown_filter` and an unknown sort key a 422 `unknown_sort`. Embed `PageParams` in the input, call `in.parse(rules)` for the `page.Request`, run a keyset query for `Limit+1` rows, and cut the page with `page.Slice`. Return a `collectionOutput[Row]`. A row embeds the full resource and adds `Version`. Register the handler as `listing(handler)`. Give the `collectionRules` a name, and mark a time key `Time: true`, so `page.Parse` checks the cursor's value. A cursor from another sort or another collection is a 422 `cursor_mismatch`. A cursor the server can't read is a 422 `invalid_input`, never a 500: `listing` turns a `page.ErrBadCursor` from a domain package into that 422 too.
- **A full resource.** Return `resourceOf(body)` or, for a create, `createdOf(path, body)`. They set the `ETag`: `versionOf` hashes the resource as this caller sees it (the JSON of the body struct, without the `$schema` property that huma adds to the bytes it sends), not the response bytes. A collection row's `version` is the same string. Don't change it to hash the bytes: the tag would then change with the Host.
- **An edit.** Make the body `MergePatch[Changes]`, where `Changes` is a struct of `Field[T]`s. Call `Refuse(writable, visible)` first: a field the caller sees but can't change is a 403 `field_not_writable`. Pass the domain package a `patch.Optional` for each field, and a guard that calls `checkIfMatch`. The guard runs inside the write's transaction, so a 412 `resource_changed` never races with another write. Call `acceptMergePatch` after you register the route, so the document lists `application/merge-patch+json`.
- **A delete.** Takes `If-Match` the same way: the guard compares the version of the row as the caller sees it.

## Who can see a user, and fields that only some callers see

The rule of who can see a user is in one place: `visibleTo` in `internal/user/visible.go`. It is a SQL condition on a `users` row, and the Go code never repeats it. `GET /users`, its `total_count`, `GET /users/{id}`, a group's users, and the check that an avatar may load all use it, through `Service.Visible`, `Service.InGroup`, `Service.GetVisible`, `user.CanSee`, and `user.CanSeeSummary` (a user's summary also reaches the viewers who see their parent or child, so the avatar loads for them). A change that makes more users visible or fewer (a deactivated user) changes `visibleTo` and nothing else. A parent and a child see each other there, and only through direct links. The rule of who can see a group is in the same file (`GroupSeenBy`, built on `GroupsContaining`), and `internal/group` uses it, so the `up` set of groups that contain a user has one copy. A route that has a transaction open calls `user.CanSee` with the transaction, and never with the database handle.

What a parent may do for a child is one function too: `canActFor(caller, target)` in `internal/server/loginlinks.go` (the user, a parent in `target.Parents`, or the admin). The routes and the `can_*` fields call it and never repeat it. Every `user.User` comes with its `Parents` and `Children`, so the check costs no query. The user must be active: `canActFor` is `actsFor` (the role) and an active user, while `actsFor` alone gates the reads, which a deactivated user keeps. A route that writes through the role loads the user with `userToWriteFor` and checks `writeAccess` again inside the write's transaction (`stillMayWriteFor`), so a request that races an unlink or a deactivation can't succeed.

A field that some callers must not see is a `Private[T]` in the body (`internal/server/private.go`):

- Tag it `json:"name,omitzero" required:"false"`. A caller who may not see it gets no key at all, not `null`: `null` would say that the user has no value.
- Fill it with `Shown(value)` only where a function that names the rule says so (`seesPrivateFields` for `timezone` and `profile_confirmed_at`). `Shown(nil)` is `null`, for a caller who sees the field and the user has no value.
- Nothing else is needed. The `ETag` and a row's `version` hash the body the caller gets, so a change to a field the caller can't see doesn't move their version. `Refuse` reads the keys of that same body, so a hidden field is not a field the caller can change.

## Who can see a list, who can edit one, and the admin check

The rule of who can see a list is `list.VisibleTo`, and the rule of who can edit one is `list.EditableBy`, both in `internal/list/rules.go`. Each is a SQL condition on a `lists` row, and nothing else repeats it: `GET /lists`, its `total_count` and the `?can_edit=` filter, a list's own address, the items of a list (`internal/item` joins the item's list as `lists`, so the same conditions apply), and the `can_*` fields all call them. A change that widens a rule (a list is seen through any of its recipients, a recipient's parent edits) changes the condition there. `list.SeesPrimaryListOf` is the same rule for a user's `primary_list` field, in the same file. A list or an item the caller can't see is a 404. One they see and can't change is a 403 `forbidden`, checked before the body.

A primary list is made by `user.Create`, the one function that inserts a user, so setup, `POST /users`, and a test that makes a user all get one. A rename of the user renames the list in the same transaction while the list still follows the user's name (`lists.name_follows_user`).

An invitation has a visibility rule of its own, `list.InvitationVisibleTo` in the same file: the invited user, their parents, and the list's recipients. It doesn't follow the list or the user, and the admin has no access of it. `GET /invitations`, an invitation's address, its `can_*` fields, and the avatars in an invitation (`list.SummaryReaches`) all call it. Who can be invited is `list.InvitableUsers`, built on `user.VisibleToWithoutAdminAccess`, and `GET /users?invitable_to=` and `POST /lists/{id}/invitations` both follow it. Leaving has one rule too, `List.CanRemove`: a list's `can_leave` and a recipient's `can_delete` call it, and so does the route. `list.SeesListAfterLeaving` is the rule of a recipient's `sees_list_after_leaving`. A parent's powers through a deactivated child stop in these rules, not in the routes: `list.UserOrTheirActiveParent` is the write role of "the user or their parent" (editing and leaving), and `list.UserOrTheirParent` stays the read role (an invitation, the leave warning). A caller who sees a list and can't edit it gets `list.NotEditable`, which says `ErrRecipientDeactivated` when they are the parent of a deactivated recipient and `ErrNotEditable` otherwise. The routes turn the first into a 403 `user_deactivated` (`Server.cannotEdit`) and the second into a 403 `forbidden`, so a new route that checks `CanEdit` calls one of them and never writes `forbidden(...)` itself.

A route that only the admin may call asks `requireAdmin(ctx, "does the thing")` (`internal/server/auth.go`). Don't write the check again.

A query parameter that tells "not sent" from `false` (`?can_edit=false`) is an `OptionalParam[bool]` in the route's input. huma has no pointer parameters.

## Who can see an occasion, and its next date

The rule of who can see an occasion is `occasion.VisibleTo`, and the rule of who can change one is `occasion.Occasion.EditError` (with `occasion.ManagedBy` for the SQL, and `occasion.CanAddFor` for a user's `can_add_occasion`), all in `internal/occasion`. An occasion is seen through its user: a birthday follows `user.VisibleTo`, and a custom occasion follows `user.VisibleToWithoutAdminAccess`, so the admin's access shows no custom occasion. The user and their parent change a custom occasion while the user is active, and nobody changes a birthday (403 `birthday`). The writes load the occasion again inside their transaction, so an unlink or a deactivation that commits first stops them.

A birthday occasion is a row with no date rule of its own (`rule_kind` is `NULL`). Its rule is built from the user's birthday each time it is read, so editing the birthday needs no sync. `user.Create` makes the row, so every path that makes a user makes it.

A shared occasion has no user and reaches users through `occasion_groups` (and with nesting, through `group_groups`) or, when `occasions.is_everyone` is set, every user. `occasion.VisibleTo` shows it to the admin and to every user who sees a user it applies to, `reachCTE` in `rules.go` is the one copy of "the groups an occasion reaches", and `appliesToWhere` and `AppliesToUser` (same file) say who an occasion applies to, for `GET /users?occasion_id=` and `GET /occasions?user_id=`. Marking an occasion everyone clears its attached groups in the same transaction, so an everyone occasion never has groups.

`next_date` is not a column: it depends on the clock and on the timezone of the occasion's user (a shared occasion has no user, so the caller's timezone; a user with none is in the fallback zone), so `GET /occasions` loads the visible rows, works out the dates, and sorts and pages them in Go (`Service.Visible`). A cursor holds the sort key of the last row, and the ID. The date rules are in `internal/occasion/occasion.go` and use no clock of their own.

## Who can see a gift, and the claim state of an item

A gift is one record for its whole life (ADR 0011): `given_at` is `NULL` while it is open. The rule of who can see a gift is `gift.VisibleTo` in `internal/gift/rules.go`, a SQL condition on a `gifts` row, and nowhere else: its giver, and once it is given its recipients (`gift_recipients`) and their parents (`user_parents`). `GET /gifts`, a gift's own address, its `can_*` fields, every write, `gift.CanSee` (the visibility of the image a gift keeps) and `gift.SummaryReaches` (the avatars of its giver and recipients) call it. A gift that the caller can't see is a 404, whether or not they can see its item.

A field that is only the giver's (`note`, `is_bought`, `created_at`, and the `flags` and `needs_attention` of an open gift) is left out of the domain `Gift` for anyone else (`Gift.IsGiver`), and is a `Private[T]` in the body, so a recipient's response has no such key. A new giver-only field follows the same two steps.

The claim state of an item is a giver's, and a giver is anyone who sees the list and isn't a recipient. Three rules, each in one place:

- `list.ItemShownTo` (`internal/list/rules.go`) says which items a viewer sees on a list they can see. Nobody sees a soft-deleted item. A recipient sees every other item. A giver doesn't see an item that is fully claimed, unless they have an open gift on it. The items of a list, an item's address, a list's `item_count`, the avatars reached through `added_by` (`list.SummaryReaches`) and the images of an item all call it. A new query on `items` that a user can reach must call it too.
- `list.GivableRecipients` says which recipients a giver can give to: not themselves, visible to them, and active. `can_claim` on an item and the occasions a giver can pick (`occasion.PickableFor`, behind `GET /occasions?list_id=`) both follow it.
- `item.Item.Claim` holds `still_wanted`, `my_claimed_quantity` and `can_claim`, and is `nil` for a recipient. The body fills the three fields only when it isn't `nil` (`Private[T]`), so a recipient gets no key.

A claim and every change of a quantity run in one transaction with the check of how many are still wanted, and the database lets one writer at a time, so two givers who claim the last one at once are serialized: the second gets 409 `item_fully_claimed`. A claim finds its item without `ItemShownTo`, because the role of a giver is "sees the list" and a lost race must be a 409, not a 404. The 404 is for an item that is gone or not on a list the caller sees.

`item.Service.remove` is the one place that deletes an item. An item that has any gift is deleted softly (`items.deleted_at`): it keeps its row, images and store links, so the gift keeps what it was given, and `item.PurgeIfUnused` removes it for good when the last gift goes. Queries that count or move the items of a list ignore soft-deleted rows.

## Flags on a gift, and a list kept for its gifts

A flag says that something happened to an open gift that its giver should answer. Only the giver sees flags, and nothing in the recipients' views reads them. `internal/giftflag` owns the tables (`gift_flags`, `gift_changes`) and every write. It imports no other package of the app, so `internal/item` can set flags and `internal/gift` can show and clear them. A write takes the transaction of the change that causes it, so the change and its flags commit together. Every write goes through "the open gifts of the item", so a given gift is never flagged.

- **Where flags are set.** `item.Service.Update` (an edit, a new primary image, a move), the store link writes (`ChangeStoreLink`, `DeleteStoreLink`, `SavePrices`), and `item.Service.remove`, the one place that deletes an item (flag `removed` for a soft delete). `internal/item/flags.go` holds the rules for what flags: the first price an item or a store link ever has does not, a refresh with no price change does not, a picture other than the primary image does not, and adding a store link does not. A new item write that a giver would notice calls `giftflag.ItemChanged` with its lines.
- **The diff.** A `changed` flag exists exactly while the gift has lines in `gift_changes`. A field that changes again keeps its first old value, and a line goes away when the field changes back. Values are JSON, so a price is `{price_minor, top_price_minor, currency}` or `null`.
- **Clearing.** `POST /gifts/{id}/acknowledge` calls `gift.Service.Acknowledge`. Clearing `changed` drops its diff. When a gift merges into another (`Service.merge`), `giftflag.Merge` adds its flags to the staying gift's.
- **Attention.** `needs_attention` is computed in `gift.Service.build`: not bought and revealed within 14 days, or flagged `changed` or `removed`. The `?needs_attention=` filter keeps the gifts whose computed value matches, like `?occasion_id=`. Home asks for `needs_attention=true`.
- **Deleting a list with kept gifts.** `list.Service.Delete` deletes each item through `item.Service.RemoveAllOn`. If items are left (they have gifts), the list keeps its `lists` row with `deleted_at` set, its recipients move to `kept_list_recipients`, and its invitations go. With no row in `list_recipients`, no rule of `internal/list` matches the list, so nobody sees it. The gift still reads its list's name, and `recipientZones` reads the kept recipients, so the reveal moment doesn't change. `item.PurgeIfUnused` removes the shell with the last gift. A rule that must count a deleted list's recipients (reveal, the deletion of a user) reads `kept_list_recipients` too.

## Keeping open gifts right when something changes under them

A change to a list's recipients, to an occasion, to a birthday, or to the list an item is on can make an open gift wrong. `internal/gift/settle.go` holds the one rule that puts it right, `Service.settle`, and nothing else repeats it. The package that makes the change doesn't import `internal/gift` (it would be a cycle). It has an `Observer` interface (`list`, `occasion`, `user`, `item` and `group` each have one) that it calls inside the transaction of the change, so the change and what it does to the gifts commit together, and an error undoes both. `gift.Service.Watch` registers the one implementation. `cmd/wishbone/main.go` and the test server (`testOptions`) call it, so a new `Service` for those five packages in another place (a CLI command, a test) must call it too if its writes can change a gift.

- `settle` looks at the state after the change and has no memory of what the change was, so running it again is safe. For each open gift in its scope: it releases the gift when the giver is the only recipient, flags `no_longer_shared` once when the giver comes to see none of the recipients (`gifts.unshared` remembers it, so an answered flag stays answered), and moves the gift to the next upcoming occasion, flagged `occasion_moved`, when its occasion applies to none of the recipients the giver can see. When the giver sees none, the occasion must apply to some recipient other than the giver, and the pick is among all of them (`occasion.Service.UpcomingFor`). A move that lands on an occasion the giver has a gift for merges, as `Service.merge` does.
- `redate` is for a change of an occasion's date rule or a birthday: a gift for the occasion moves to its new next date, in the same occasion. A gift whose occasion date has passed waits for its reveal and never moves.
- A change in the recipients also raises `recipients_changed` first (`giftflag.ChangeRecipients`), which needs the recipients from before: `list.Observer.RecipientsChanged` gets them.
- An occasion's delete runs `settle` before the `DELETE`, with the occasion counted as gone, because `gifts.occasion_id` is `ON DELETE SET NULL`. What is left pointing at it is a gift past its date, or a given gift.
- Who sees whom changes with a user in or out of a group, a group nested or unnested or deleted (`group.Service`), and a parent link (`user.Service.Update`). Each calls `VisibilityChanged` with the users it can affect: the users in the groups around the one that changed (`group.usersAround`, before and after the change), or the child and its old and new parents. `settle` then looks at the open gifts those users give or are recipients of, so `no_longer_shared` and an occasion move happen at the change itself.
- A gift kept on a deleted list is settled too, with the list's last recipients from `kept_list_recipients`. The giver sees none of them, so the server picks the occasion among all of them. The gift is not released, and not flagged `no_longer_shared` (the list's delete flagged it `removed`).
- `wishbone set-admin` moves the admin role through `watchedUsers` (`cmd/wishbone/watched.go`), a user service with the gift observer, because the admin sees every user and the move changes what the old and new admin can give to.
- A gift that moves onto an occasion the giver already has a gift for merges into that one, also when its date has passed and it waits for its reveal (the unique index allows one open gift for each item, giver and occasion). The window is the hours before the latest recipient's midnight.
- `user.Service.Deactivate` and `Reactivate` call the observer in their own transaction. `Deactivated` releases the gifts the user was giving (`Service.releaseOf`: each is deleted as an unclaim deletes it, so its quantity is back on the item at once, and the gifts they gave stay), then `VisibilityChanged` settles the rest, because `list.GivableRecipients` counts a deactivated recipient as one no giver can see. Reactivation settles again, and leaves a gift that moved or was flagged as it is. A recipient reads nothing of this: the item, its `version`, `item_count` and its images are the same before and after (`internal/server/deactivation_gifts_test.go`).
- A new event that can make a gift wrong adds a call to `settle` with a `scope`. It adds no second copy of the rule. The deletion of a user (see [Deleting a user](#deleting-a-user)) is the latest: it leaves lists through `list.Service.RemoveRecipient`, which calls the observer, and it calls `settle` itself for the lists kept earlier and for the gifts that are still for one of the user's occasions.

## Deleting a user

`wishbone delete-user <id>` (`cmd/wishbone/deleteuser.go`) shows `userdelete.Service.Plan`, asks for the user's name (`--yes` skips it), and runs `userdelete.Service.Delete`. The rules are in [Deletion](spec.md#deletion). The command builds its services with `watchedDeleter` (`cmd/wishbone/watched.go`), which registers the gift observer like the server does, so the delete flags and settles gifts in its own transaction. It refuses the admin and a database with a migration pending (`openMigrated`). After the commit it runs the image sweep over the data dir, so the files of the images that went are removed without a server running.

`internal/userdelete` is one transaction, and the order of its steps in `Service.forget` matters:

1. The gifts the user gave keep their name (`gifts.giver_name`; `giver_id` becomes `NULL` with the row, and `gift.selectSQL` reads `COALESCE(users.name, gifts.giver_name)`). Their open gifts are released (`gift.Service.ReleaseOf`).
2. The given gifts that only the user received are deleted (`DeleteGivenOnlyTo`). The quantity does not go back on the item: it left at reveal, and a quantity that came back would show a recipient who joined later that the item had been given. A given gift for the user and others loses only the user's row in `gift_recipients`.
3. For each list the user is a recipient of: with another recipient, `list.Service.RemoveRecipient` (the same code as `Leave`) flags the open gifts there `recipients_changed` and settles them. As the only recipient, the open gifts there are deleted with no gift kept for their giver (`DeleteOpenOn`), then `item.Service.RemoveAllOn` and `list.Service.Remove`, which keeps the list as a shell when a given gift still needs an item on it. The user's primary list is made nobody's first (`primary_user_id` is `ON DELETE CASCADE`, and the cascade would delete the shell and the given gifts with it).
4. The lists kept earlier for their gifts forget the user as a last recipient (`ForgetKeptRecipient`). An open gift on such a list with no recipient left but its own giver is deleted, because a gift is never for its giver. A list kept for its giver alone from the start is not touched, as Restore does not touch it. The rest are settled.
5. `SettleOccasionsOf` settles any gift that is still for one of the user's occasions, with the user no longer a recipient anywhere.
6. `giftflag.ForgetUser` drops the user from `recipients_changed` flags (old and new) and from `restored` flags. It runs after step 3, which raises flags that name the user as an old recipient.
7. The user's avatar is detached, and so is every image they uploaded that nothing holds (`image.DetachUnheldBy`). An image that another resource holds stays, and `images.uploaded_by` becomes `NULL`.
8. The `users` row goes. `sessions`, `login_links`, `passkeys`, `user_parents`, `group_users`, `occasions` and `list_invitations.user_id` cascade, and `items.added_by` and `list_invitations.invited_by` become `NULL`.

A step that reads a flag or a quantity a remaining recipient could see would be a leak, so none of the steps above changes an item on a list that stays. `internal/server/user_delete_privacy_test.go` reads the lists, items, images and gifts of the remaining recipients before and after, and requires the same bodies and ETags.

## Reveal

`gift.Revealer` (`internal/gift/reveal.go`) gives the gifts whose moment has come. `cmd/wishbone` runs `Schedule` at start (the catch-up after downtime) and every 5 minutes. A gift's moment is `revealAt` in `internal/gift/gift.go`: the latest of its recipients' midnights after the occasion date, with the giver left out, and a recipient with no known timezone in the fallback zone (the server's `TZ`, which `cmd/wishbone` passes to `NewRevealer` and `occasion.WithFallbackZone`; tests pass their own). `Gift.RevealAt` and the scheduler both call it, so what a client reads is when the gift is given. A list that was deleted with its gifts kept counts its `kept_list_recipients`.

Each gift is given in a transaction of its own, and only if it is still open (`UPDATE ... WHERE given_at IS NULL`), so two runs, or a crash, never give it twice. The transaction:

- sets `given_at` and copies the item's title, price and the occasion's name onto the gift (`gifts.title`, `price_minor`, `top_price_minor`, `currency`, `occasion_name`);
- copies the primary image as a new image of the gift's own (`image.Service.Copy`, `gifts.image_id`). A gift holds an image as an item does (see [Images](#images)), so the sweep keeps it and it loads for whoever sees the gift. If the transaction fails, the new file is deleted (`Service.Discard`);
- records the recipients (`gift_recipients`), the list's at that moment without the giver;
- records whether the giver could see the list and the occasion (`giver_saw_list`, `giver_saw_occasion`), because routes.md shows a giver of a given gift only what they could see at reveal;
- clears the gift's flags: a given gift has none;
- takes the quantity off the item (`item.Given`). An unlimited item is left alone, and so is an item that is deleted already: a user's delete keeps the quantity the item had. An item with quantity left stays on its list. An item whose whole quantity was given gets quantity 0 and is soft-deleted, the items after it close the gap, and its other open gifts (givers who claimed more than was left) are flagged `removed`, as a user's delete flags them. So a deleted item with quantity 0 is exactly an item that left its list because it was given, and a restore tells it from one that a user deleted (`items.quantity` allows 0);
- lets go of the copy of the image that an earlier reveal made, when the gift was restored since (`image.Detach`), so the sweep deletes the old image.

A gift with a copy (`gifts.title` is not NULL) shows the copy, whatever its `given_at`, so a restore only has to clear `given_at` and the recipients. A gift that is given reads its recipients from `gift_recipients`, and an open one from the list.

## Restore and Add again

`gift.Service.Restore` (`internal/gift/restore.go`) is `POST /gifts/{id}/restore`. Who can restore is `gift.ReceivedBy` (a SQL condition on a `gifts` row: a given gift that the viewer receives, as a recipient or the parent of a recipient who is active); `can_restore` and `can_add_again` are `gift.CanRestoreOf`. `VisibleTo` does not use it: a parent keeps the read of a gift given to a deactivated child, and loses restore and Add again. A parent in that case gets `ErrUserDeactivated` (`notReceived`), a 403 `user_deactivated`, from both routes. A giver who is not also a recipient's parent sees the gift and gets a 403 `forbidden`. A gift the caller can't see is a 404, the same one as a gift that doesn't exist.

- **The quantity.** `item.Restored` works from what the item has left, not from what it had: a live item gets the gift's quantity added (an unlimited one needs nothing), and an item that left its list because it was given (deleted, quantity 0) gets the quantity as its whole quantity and goes to the last place on its list. The open gifts that were flagged `removed` when it left lose that flag. An item that a user deleted, or whose list was deleted (`lists.deleted_at`), stays deleted and its quantity is not touched; the gift is flagged `removed`.
- **A gift that opens again.** `given_at`, `giver_saw_*` and its `gift_recipients` are cleared, and the copy stays until the next reveal copies again. It is flagged `restored` with `by` (the flag's data). Its occasion is `Service.nextOccasions` (the one rule of `settle` and of restore): the occasions the giver may pick, or the upcoming occasions of the other recipients when the giver sees none. If the giver has an open gift on the item for that occasion, the restored gift merges into it (`moveOccasion`, which sets `given_at` in the same statement, because the unique index allows one open gift for an item, a giver and an occasion). Then `settle` runs for the gift, so a giver who can't see the list is flagged `no_longer_shared` as for any open gift. `occasion_moved` is not raised: the restore is the news.
- **A gift that is deleted.** When the giver is deleted, deactivated, or the only recipient of the list now (the rule that releases an open gift), the gift is deleted (`Service.deleteGift`, which detaches its copy of the image) and the quantity goes back unclaimed. `deleteGift` is the one place that deletes a gift, so a copy is never left for 24 hours.
- **`by` is the giver's view.** `loadFlags` shows the user only when `user.VisibleTo(giver)` matches them.
- **Privacy.** After a restore the gift is a 404 for the recipients and their parents, its image and its giver's avatar stop loading for them (`gift.CanSee` and `gift.SummaryReaches` need `given_at`), and the item is the item as it was before it was claimed (same body, same ETag, same `item_count`). Tests in `internal/server/gifts_restore_test.go` check each.

Add again is `POST /lists/{id}/items` with `from_gift_id`. `server.addAgain` asks `gift.Service.AddAgainSource`, which reads only the gift (its copy), so the answer says nothing of the gift's item: a 403 `reference_not_allowed` for the giver, a 422 `reference_not_found` for anyone who can't see the gift (also a gift that isn't given yet or was restored). The title comes from the gift unless the body has one. The price fields (`price_minor`, `top_price_minor`, `currency`) come from the body together if it has any of them, and from the gift together otherwise. The image is copied as a new image in the add's transaction (`item.New.ImageFrom`, `image.Service.Copy`) unless the body has `image_ids`, an empty array too (it means no image); the route removes the file if the add fails.

## Blocked stores

A route that takes a URL from a user (adding a store link, search) asks one question: `Options.Blocked.Match(ctx, rawURL)` in `internal/blocklist`. It returns the blocked store as listed (`temu.com` for `https://m.temu.com./p`), whether the URL is blocked, and an error. It matches the host and its subdomains, and ignores a trailing dot, `www.`, a port, case, and full-width letters (`extract.StoreFromURL` makes the host canonical). A string that isn't a web address is never blocked. A URL with a cached reading is checked at the address the reading ended at too, so a short link is caught without a fetch. A blocked URL is a 422 `store_blocked` (docs/routes.md); the route builds that error, because the check only answers.

Two rules keep `Match` from letting a link through:

- **Normalize and parse the URL first.** `Match` answers "not blocked" for an address it can't parse, so a route must never pass it a raw string and trust the answer. Call `Server.unblockedAddress` (`internal/server/search.go`): it runs `extract.NormalizeURL`, answers a 422 `invalid_input` for an address that doesn't parse, and then asks `Match`. It returns the normalized address, and the route uses that one from then on. Search and the store links of a new item both use it.
- **Ask again about the address after redirects.** A link that redirects to a blocked store is found only after the fetch. Search calls `unblockedAddress` a second time on the address the pipeline ended at (`pipeline.Result.URL`). That refusal counts against the hourly limit, because the fetch happened. The first check, before any fetch, does not.

## Search and the hourly limit

`POST /search` (`internal/server/search.go`) takes a multipart form with exactly one of `text` or `image`. The handler reads the form itself (`parseSearchForm`) and keeps no copy of a photo.

- A link goes through `pipeline.Service.Extract` (`internal/extract/pipeline`): the 24-hour cache, then a direct fetch, Bright Data Web Unlocker, and the LLM. A link on the instance's own network (`netguard`) ends the pipeline with nothing found, so neither Bright Data nor the LLM sees it. `cmd/wishbone/extractor.go` builds the pipeline from the config; a stage without its settings is skipped.
- The hourly limit (30 links and photos per user in any rolling 60 minutes) is the pipeline's own limiter, so a cache hit, free text, and a photo when the LLM is off cost nothing. The routes that read a page again (adding a store link to an item, refreshing prices) call the pipeline too, through `Server.readLink` (`internal/server/search.go`), so they count against the same limit. `readLink` asks `unblockedAddress` about the address the page ended at. A refresh passes `pipeline.BypassCache()`, so each read counts. It asks `unblockedAddress` about each stored address first, so it doesn't read a link in a store blocked since the link was added. A database error there stops the refresh, and the prices already read are still saved.
- `POST /images` with `{"url"}` downloads through `imagestore.Store.DownloadPut`, which uses the same `netguard` rule. It never touches the limiter.

## Images

An image is a row in `images` that names a file in the image store (`internal/image`, `internal/imagestore`). A client uploads it with `POST /images`, then attaches it by ID. The rules are in [Images](spec.md#images). To let a new resource hold an image:

- **Add a column** that refers to `images(id)`, with a unique index, as `users.avatar_image_id` does. That column is the attachment. The foreign key has no `ON DELETE` action, so the database refuses to delete an image that a row still holds. A resource with several images has a table of its own for them, as `item_images` is: a row per image, with a unique index on `image_id`. Its owner detaches the images in the same transaction that deletes the owner.
- **Add it to the image package**: a `SELECT` in `heldSQL`, and a `Kind` and a case in `AttachedTo`. Add the resource's rule to `imageVisible` in `internal/server/images.go`.
- **Check the ID in the write's guard**, with `attachableImage`: a 422 `reference_not_found` for an image the caller can't see, and a 409 `image_attached` for one that another resource holds. Call `image.Detach` in the same transaction when a change lets go of an image. The backup needs nothing new: `imagerefs` reads every key in `images`.

The sweep (`image.Service.Sweep`, hourly and at start) deletes the rows that nothing holds and that were detached or are 24 hours old, and only then their files. It never lists the files in the data dir, so it can't delete a file that a row refers to or that a migration has not given a row yet. Don't add a sweep of files with no row.

## Snapshots and the version guard

Backup, restore, the automatic snapshot, and the version guard are described for operators in [`operations.md`](operations.md), and in the spec's [Migration](spec.md#migration) section. This section is what a change to the code must keep true. How to write a migration is in [`development.md`](development.md#migrations).

- `wishbone backup <path>` is `internal/backup`. It uses the same `WISHBONE_DATA_DIR` as the server, or `--data-dir`. It copies the images before and after the `VACUUM INTO` of the database, so the snapshot's images exist in the backup even if the app replaces one during the run.
- The snapshot that `serve` writes before a migration reads the database as it is before the migration. `internal/imagerefs` keeps an image-key query for each schema, and the snapshot uses the one for the database's goose version. A migration that changes a table or column that holds an image key must also add an entry for the new schema to `schemas` there. Keep an entry for every version that the binary accepts (the baseline version and later): drop one only when the version guard starts to refuse those versions. The baseline's entry selects every key in `images`: each row has a file, whether or not a resource holds the row, because the sweep deletes the row before the file.
- Retention (`backup.AutomaticWithBaseline`, called with `store.BaselineVersion`) keeps the 3 newest automatic snapshots and deletes only folders whose names match `pre-migrate-<from>-to-<to>-<time>`. It never deletes a snapshot named for a move from a version below the baseline's, and the 3 newest don't count it, because it can be the only copy of that data. The version guard refuses such a database, so this binary writes no new one.
- Every command opens the database with `store.Open`, which is the version guard. It returns `store.ErrDatabaseNewer` for a database that a newer binary migrated, and `store.ErrDatabaseTooOld` for a database that has migrations but not the baseline (its version is above 0 and below `store.BaselineVersion`). `serve` opens the database before it snapshots or migrates, so a refused start writes no snapshot.
